# Разработка

Технические заметки о Vintage Story Panel. Для пользователей — [README](../README.ru.md).

Текущие архитектурные правила и форматы описаны здесь и в комментариях к коду.
Для работы с проектом внешние рабочие заметки автора не требуются.

## Сборка

```bash
dotnet build
dotnet test                         # 1882 теста, ни одному не нужен сервер
```

Нужен .NET SDK 10. Стиль — `.editorconfig` во всех файлах: табы, CRLF, приватные поля
camelCase без `_`, в `.js` одинарные кавычки. Проверки C#:

```bash
dotnet format whitespace --verify-no-changes
dotnet format style --verify-no-changes --severity warn
```

Обе проверки выполняются в CI на Linux и в `scripts/release.ps1`.
Они не заменяют проверку остальных текстовых файлов на соответствие `.editorconfig`.

Всё, что исполняет или разбирает Linux (`scripts/*.sh` и `deploy/`, кроме
`deploy/windows/`), — с LF. Это проверяет тест, а `.gitattributes` защищает репозиторий,
но не копию дерева на сервере.

CI (`.github/workflows/ci.yml`) на каждый push в `master` и на pull request собирает решение,
гоняет тесты и проверяет стиль на Linux; правка только текстов и скриншотов его не
запускает. Тесты на Windows и пакеты всех трёх целей запускаются по тегу релиза или вручную
(Actions → CI → Run workflow); артефакты Actions хранятся один день: self-contained пакет весит сотни мегабайт, а квота
хранилища Actions общая на аккаунт. Мод телеметрии в них входит.

Зависимости проверяются на известные уязвимости дважды. При каждом `restore` аудит NuGet
(`NuGetAuditMode=all` в `Directory.Build.props`) превращает уязвимость любого пакета, включая
транзитивные, в ошибку сборки; недоступный источник сведений (сборка без сети) остаётся
предупреждением. Раз в неделю и при правке `*.csproj` то же проверяет
`.github/workflows/audit.yml`: уязвимость, опубликованная после последнего пуша, иначе не
была бы замечена. Обновления пакетов и действий Actions предлагает Dependabot
(`.github/dependabot.yml`).

### Поставка

На Windows публикуйте из PowerShell в корне репозитория; Bash и WSL не нужны:

```powershell
.\scripts\publish.ps1 win-x64
```

Из `cmd.exe` запускайте тот же сценарий через штатный Windows PowerShell:

```cmd
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\publish.ps1 win-x64
```

Нужен .NET SDK 10. Если PowerShell запрещает запуск `.ps1`, используйте приведённую
команду с `-ExecutionPolicy Bypass` и в PowerShell.

На Linux используйте Bash:

```bash
bash scripts/publish.sh linux-x64
bash scripts/publish.sh linux-arm64
```

Цели проекта: `linux-x64`, `linux-arm64`, `win-x64`. Оба сценария создают
self-contained single-file пакет в `artifacts/<цель>`: три исполняемых файла,
`VERSION`, `RID`, `install.sh` или `install.cmd` и `telemetry/`.
Публикация заменяет только пакет своей цели; запуск `dotnet build` и `dotnet test`
пакет в `artifacts` не обновляет. Перед установкой проверьте `artifacts/<цель>/VERSION`
и время изменения исполняемых файлов.

Мод телеметрии (`vspaneltelemetry_*.zip`) лежит в `telemetry/` и входит в каждый пакет;
установщик кладёт его в моды серверов. Другой каталог с модом задаёт `VS_TELEMETRY_DIST`.
Без мода панель ставится, но готовность серверов видит ограниченно: наблюдатель и
автоперезапуск работают хуже. Новая версия мода — новый архив в `telemetry/` вместо
прежнего: в пакет попадают все архивы каталога.

### Релиз

Для подготовки версии используйте `pwsh -File scripts/release.ps1 -Version <версия>`.
Скрипт меняет номер, создаёт шаблон описания и запускает проверки; режим `-Mode Check`
проверяет итоговый коммит перед тегом. Пошаговая инструкция — [Подготовка новой версии](releasing.md).

Релиз публикует тег `v<версия>`; версия обязана совпадать с `PanelVersion` в
`Directory.Build.props`, иначе задание `release` в CI отказывает. CI собирает три пакета,
проверяет решение на Linux и Windows, упаковывает каждый с каталогом `vs-panel-<цель>` внутри (`vs-panel-linux-x64.tar.gz`,
`vs-panel-linux-arm64.tar.gz`, `vs-panel-win-x64.zip`), считает `SHA256SUMS` и создаёт
GitHub Release. В него также входят `get.sh` и `get.ps1` из того же коммита; суммы
считаются и для них. Публикация идёт через черновик: пока все вложения не загружены,
`releases/latest` его не отдаёт. Тег с дефисом (`v0.5.0-rc.1`) — пререлиз: «последним» он не считается.

До загрузки каждый архив проверяет `scripts/verify-release.py`: каталог, версия и цель,
три бинарника, установщик, мод телеметрии, безопасные имена записей, владелец и права
Linux, окончания строк установщика. Перед созданием релиза `--all` требует все три
архива. Ручной запуск тоже выдаёт готовые `.tar.gz` и `.zip`: скачивание артефактов Actions
не теряет права внутри tar. Описание версии лежит в `docs/releases/<версия>.md`.

Из релиза ставят три входа, и все читают его одинаково: тег выбирается один раз (явная
версия или `releases/latest` API GitHub), затем из этого тега берутся `SHA256SUMS` и архив.
- `deploy/get.sh` — `curl … | sudo sh`, затем `install.sh` из архива. Скрипт целиком
  внутри `main`: обрыв загрузки не запустит половину.
- `deploy/windows/get.ps1` — `irm … | iex`, затем `Panel.Cli.exe install --from`. Только
  ASCII (`iex` не знает кодировки). Без прав администратора перезапускается через
  `RunAs`, передавая ключи в команде: окружение повышенный процесс не наследует. Каталог
  распаковки — только SYSTEM и администраторы, иначе обычный процесс того же
  пользователя мог бы подменить `Panel.Cli.exe` между проверкой суммы и запуском.
- `vs-panel install|update` без `--from` (`ReleaseSource`) — распаковка в
  `<каталог программы>/downloads` по той же причине. Последний релиз не ставится
  поверх более новой версии (пререлиза или своей сборки, `CompareVersions`): новая версия
  читает состояние прежней, но не наоборот. `update` до уже стоящей версии ничего не
  делает; `--version` ставит заданную, на Linux и ту же заново. На Windows та же версия
  отказывает до загрузки: `vs-panel` в PATH запущен из `current`, а его установщик не
  заменяет (`CheckNotRunningFrom`) — переустанавливают `get.ps1` или `install.cmd`.
  Пакета `win-arm64` нет: `win-x64` на ARM64 установщик не примет.

Сумма из того же релиза защищает от порчи при загрузке, но не от подмены самого релиза.
Скрипты берутся из `master` (`raw.githubusercontent.com`): их имена архивов не должны
расходиться с тем, что публикует CI. Загрузка анонимная: репозиторий публичный, токен не
нужен ни скриптам, ни `vs-panel`.

### Значок

Исходник — `scripts/icons.ps1`: геометрия знака `brand-mark` и контур буквы из Georgia.
На Windows команда `pwsh scripts/icons.ps1` (System.Drawing) пересобирает все форматы:
- `Static/favicon.svg` — знак в панели, мастере установки, README и браузере;
- `Static/favicon.ico` — стандартный `/favicon.ico` для браузеров, которые запрашивают
  значок сайта без учёта ссылок на странице;
- `assets/vs-panel.ico` — значок `vs-panel.exe`, `vs-panel-web.exe` и `vs-panel-agent.exe`

- `Static/favicon-32.png` и `Static/apple-touch-icon.png` — для браузеров без SVG и для
  ярлыка на телефоне.

Сгенерированные файлы хранятся в репозитории. При смене знака правьте только скрипт.

## Два процесса, две роли

**`Panel.Agent`** — привилегированный демон.
- **Linux:** работает от root, слушает Unix-сокет, проверяет uid подключившегося через
  `SO_PEERCRED` и отвечает одной строкой JSON.
- **Windows:** служба от LocalSystem. Сам держит игровые серверы дочерними процессами:
  их stdin — консоль, вывод — `run\<id>.console.log`. Слушает именованный канал, открытый
  только своей учётной записи, администраторам и тем, кто назван в `--allow-sid`.
- Пути выводит сам из реестра: панель присылает только идентификатор сервера.

Доверие между процессами взаимное. На Windows панель подключается к каналу с уровнем
олицетворения `Identification` (сервер канала не может действовать от её имени, а она
работает от LocalSystem) и проверяет, что канал держит LocalSystem или её собственная
учётная запись (`PipeServerIdentity`, `GetNamedPipeServerProcessId`): иначе посторонний
процесс, занявший имя, пока демон перезапускается, выдал бы себя за демон. На Linux сокет
лежит в `/run/vs-panel`, который создаёт systemd от root, и подменить его без root нельзя.

В каждом запросе и ответе есть поле `build` — сборка панели (`AgentProtocol.Build`:
`PanelVersion` и коммит). Чужая сборка — не отказ: совместимость решает версия протокола `v`,
а отказ превратил бы прерванное обновление (новый демон запущен, `manage init` упал) в простой
прежней панели. Панель запоминает сборку демона из последнего ответа (`AgentClient.DaemonBuild`),
и диагностический пакет показывает обе в ключе `agent`. Поле без умолчания: ответ прежней
версии без него — «сборка неизвестна» (`?`), а не своя.

**`Panel.Web`** — веб-процесс.
- На Linux работает от непривилегированного `vs-panel` и доступа к игровым каталогам не
  имеет. Sudo ему не нужен, поэтому его юнит можно ужесточить (`deploy/vs-panel.service`).
- Интерфейс встроен в сборку ресурсами (`src/Panel.Web/Static`): ванильный JS без сборки,
  CSP без встроенных скриптов и стилей.

**`Panel.Cli`** — установщик `vs-panel`.
- Linux: root и systemd.
- Windows: администратор, службы через диспетчер служб.

Содержимое `PANEL_STATE_DIR` он не трогает сам, а зовёт `vs-panel-web manage`
от имени панели: граф служб у `manage` тот же, что у веб-процесса, поэтому первый сервер
установщик создаёт тем же кодом, что и мастер.

### Правила, которые проверяются машиной

Все — в `tests/Panel.Architecture.Tests`: нарушение валит тесты.
- Контекст не ссылается на другой контекст, только на `Panel.SharedKernel` и
  `Panel.Contracts`. Нужны два контекста сразу — обработчик живёт в `Panel.Web`.
- `System.Diagnostics.Process` существует только в `Panel.Agent` и `Panel.Cli`.
  Установщик и панель не ссылаются друг на друга: установщик зовёт `vs-panel-web manage`
  процессом.
- В доменных методах нет голого `string`; исключения (фабрики `Parse*`, `Create*`,
  `From*`, тексты для интерфейса) названы в тесте.
- Каждая команда объявляет `[Requires(Permission)]`; умолчания «разрешено» нет.
- `[MutatesServer]` стоит ровно на изменяющих маршрутах с префиксами, меняющими сервер.
- Фронтенд зовёт только существующие маршруты: адреса из `Static/*.js` сверяются с `Map*`
  в `Panel.Web/Endpoints`.
- Файлы для Linux — с LF.

### Отказы и локализация

Отказ — это `Result<T>` и `Failure`, а не исключение. Текст для человека — `Phrase`:
русский шаблон с местами `{0}` и значения. Склеивать фразы через `+` нельзя — шаблон
потеряется. В HTTP фраза уходит строкой на языке cookie `vs_lang` (английский по
умолчанию), переводы — `src/Panel.Contracts/Resources/phrases-en.json`. Новый шаблон без
перевода валит `PhraseCatalogTests`. Строки фронтенда — `Static/locales/en.js` и `ru.js`,
ключи в обоих одинаковые. Терминал (`vs-panel`, `manage`) — по-английски.

## Установщик изнутри

### Linux

`install.sh` проверяет root и архитектуру и передаёт управление `vs-panel install`:
- учётная запись `vs-panel`;
- версия в `/opt/vs-panel/releases/<версия>`, активная — ссылка `current`;
- реестр серверов — только если его нет;
- юниты демона и панели, среда .NET для игры;
- каталог серверов: вопрос в терминале, `--servers-dir` или `VS_PANEL_SERVERS_DIR`;
- первый сервер с настройками мастера, если реестр пуст (`VS_PANEL_CREATE_SERVER=0` — нет);
- доступ к панели: заданные строки `vs-panel.env` (`--access`, `--bind`, `--port`, …) и
  правила ufw для порта панели, если ufw активен;
- одноразовая ссылка на мастер — на 127.0.0.1 и по адресам машины в сети.

### Windows

`install.cmd` просит права администратора и передаёт управление `vs-panel install`:
- службы `vs-panel-agent` и `vs-panel` от LocalSystem;
- программа в `Program Files\vs-panel\releases\<версия>`, ссылка `current` в PATH;
- данные в `ProgramData\vs-panel`, доступ только SYSTEM и администраторам;
- мод телеметрии — и в уже созданные серверы;
- доступ к панели — как на Linux; правило брандмауэра одно, `Vintage Story Panel`, через `netsh`.

Службы останавливаются до копирования версии: каталог с работающим `.exe` не переименовать.

### Доступ к панели и брандмауэр

Поставка слушает `0.0.0.0` с `PANEL_ALLOWED_HOSTS=*` и `PANEL_FIREWALL=lan`.
Что открыть и кому, решает `PanelListener` (`Panel.Provisioning`). Его используют и
установщик (`PanelAccess` в `Panel.Cli`), и демон:
- параметры установки — `InstallOptions`: набор `--access localhost|lan|internet` и
  отдельные ключи поверх него; `lan` и `internet` ставят и `PANEL_ALLOWED_HOSTS=*`, иначе
  фильтр Host ответил бы 400 на обращение по адресу машины; значения проверяет `PanelSetting`, как в мастере;
- заданные строки переписываются в `vs-panel.env` на месте при `install`, `update` и
  `repair`; без ключей файл не меняется;
- смена `PANEL_BIND` или `PANEL_PORT` в мастере идёт через `panel-env-set`, и демон
  переставляет правило (`IProvisioningPlatform.SyncPanelFirewallAsync`); неудача
  возвращается полем `firewall_warning`, строка всё равно записывается;
- `PANEL_FIREWALL` не входит в `PanelSetting`: из браузера охват не меняется;
- `PANEL_TRUSTED_PROXIES` (`--trusted-proxies`) — адреса и сети обратных прокси, чьему
  `X-Forwarded-For` верит панель (`ProxyTrust`); по умолчанию петля. Значение разбирает
  `TrustedProxies`, один и тот же для установщика и панели; из браузера, как и
  `PANEL_FIREWALL`, не меняется;
- `uninstall` снимает правило панели.

Каталог серверов проверяет и готовит демон, операцией `instances-root-set`.
Требования:
- NTFS, путь без пробелов, родитель существует, сам каталог новый или пустой;
- обычный пользователь не может подменить каталог через его родителя.

Прежний каталог уходит в `former_instances_roots`. Серверы не переезжают.

Первую установку на Windows безопаснее проверять в «Песочнице Windows».

## Форматы и API

Файлы состояния, реестр серверов и `vs-panel.env` — собственный формат панели.
Менять его можно, но установки обновляются на месте: новая версия обязана читать то, что
записала прежняя.

HTTP-API не заморожен. Фронтенд живёт в этом же репозитории, поэтому адреса,
имена и форма ответов меняются вместе с ним в одной правке; `RouteTests` не даёт им
разойтись.

**API-токены.** Запрос с `Authorization: Bearer vsp_<id>_<секрет>` проверяет
`ApiTokenGuard`, а не cookie: при этом заголовке cookie сессии не читается вовсе. Токены
лежат в `api-tokens.json` (0600) хешами SHA-256 секрета; роль удостоверения — меньшая из роли
токена и текущей роли владельца, поколение учётной записи отзывает токены так же, как
сессии. CSRF для токена не проверяется (`PanelResults.Authorize`): чужой сайт не может
прислать заголовок `Authorization`. Команды с `[RequiresSession]` по токену не выполняются даже
у администратора: учётные записи, TOTP, токены, произвольная консоль, уведомления, мастер
установки, каталог серверов, создание и управление серверами. Ограничителя по адресу у токенов
нет: перебор секрета в 256 бит бессмыслен, а счётчик на адрес запирал бы рабочие токены за общим
NAT. Неверный токен дёшев: `FileApiTokenStore` помнит прочитанный набор, пока у файла те же
время правки и размер. Непрочитанный файл токенов или учётных записей — 503 из
`PanelContextMiddleware`, а не 401. Аудит пишет `user` и `api_token`; неудачное подтверждение
пароля при выпуске — `api_token_confirmation_failed`.

Выпуск удаляет только истёкшие токены; лимит учитывает текущее поколение владельца. Снимок
учётных записей мог устареть до записи, поэтому по нему нельзя удалять токены других поколений:
так потерялся бы токен, выпущенный параллельно после смены пароля. `Prune` используется только
для отображения действующих записей. Неверный тип или диапазон `created_at`/`expires_at`
исключает повреждённую запись, сохраняя остальные; ошибочный срок не означает бессрочный токен.
UI очищает секрет и поля подтверждения при выходе и новой сессии и не отображает запоздалые
ответы из прежней сессии. Регрессии UI: `node --test tests/frontend/api-token-session.test.js`.

Новая учётная запись начинает со случайного поколения (`AccountDirectory.Put`): сессии и
токены удалённой записи хранят имя и поколение, и запись с тем же именем их не воскрешает.

**`GET /metrics`** — текст Prometheus (`MetricsExposition`) из последнего замера
`ServerMonitors` и вердикта наблюдателя; демон и игра при запросе не опрашиваются. Метка
сервера — `server`, потому что `instance` Prometheus ставит сам. Право — `ExportMetrics`
(наблюдатель).

**Ревизия `serverconfig.json`** — SHA-256 канонической формы `CanonicalJson`: ключи по
кодам UTF-16, числа по точному десятичному значению без `double` (`20`, `20.0` и `2e1` — одно,
`1e20` и `100000000000000000000` тоже), минимальное экранирование.
Отметка `config-apply.json`, записанная версией 0.3.0 и раньше по форме `json.dumps`, один
раз не совпадёт, и трекер судит по времени правки файла. Сами файлы панель по-прежнему пишет
в форме `json.dumps` (`PythonJson`).

## Спайки

Проверки допущений, на которых стоит привилегированная сторона. Выполняются на целевой
Linux-машине, не на машине разработчика:

```bash
bash scripts/spikes/setpriv.sh    # setpriv понижает uid/gid до vsgame и сбрасывает дополнительные группы
bash scripts/spikes/peercred.sh   # демон видит uid подключившегося к Unix-сокету (SO_PEERCRED)
```

Пока спайк `SO_PEERCRED` не пройден, долгоживущий root-демон не подтверждён. Код это
учитывает: проверка пира на не-Linux отказывает, а не пропускает.
