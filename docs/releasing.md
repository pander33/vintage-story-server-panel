# Подготовка новой версии

Одна команда обновляет `PanelVersion`, создаёт шаблон описания релиза и проверяет
решение. Пакеты и GitHub Release собирает существующий CI после отправки тега.
Скрипт не создаёт коммиты и теги, не отправляет изменения на GitHub.

Нужны Git, PowerShell 7 (`pwsh`), .NET SDK из `global.json` и Node.js 22 или новее.
Команды ниже выполняются из корня репозитория на Windows или Linux.
Windows PowerShell 5.1 для этого сценария не подходит.

## 1. Подготовить версию

Выберите номер: исправления — следующий patch, новые функции — minor, несовместимые
изменения — major. Например, `0.4.0`; для предварительного выпуска — `0.4.0-rc.1`.
Номер передаётся без `v`, метаданные `+...` не поддерживаются.

```powershell
pwsh -File scripts/release.ps1 -Version 0.4.0 -WhatIf
pwsh -File scripts/release.ps1 -Version 0.4.0
```

Первая команда показывает действие, вторая:

- меняет только `PanelVersion` в `Directory.Build.props`;
- создаёт `docs/releases/0.4.0.md`, если его ещё нет;
- запускает restore с аудитом зависимостей, проверки форматирования и стиля C#, Release-сборку,
  все тесты .NET, тесты фронтенда и проверку пробелов Git.

Шаблон описания написан по-английски, как существующие релизы. Заполните разделы,
удалите ненужные и все метки `TODO`. Укажите совместимость обновления, изменения
формата состояния, результаты проверок и известные ограничения. Не заявляйте
интеграционные проверки, которые ещё не выполнялись на целевых машинах.

Повторный запуск сохраняет написанное описание. Если проверка упала, версия и
описание остаются в рабочем дереве: исправьте причину и повторите команду.
Существующий локальный тег с тем же номером вызывает отказ. Скрипт не проверяет
наличие удалённого тега: перед выбором номера обновите список через `git fetch origin --tags`.

## 2. Проверить и сохранить изменения

```powershell
git diff
git status --short
git add Directory.Build.props docs/releases/0.4.0.md
git commit -m "Release 0.4.0"
pwsh -File scripts/release.ps1 -Version 0.4.0 -Mode Check
```

Изменения самого продукта должны быть включены в историю до выпуска. Добавляйте
их в коммиты явно после просмотра, отдельно от команды выше.

`Check` требует чистое рабочее дерево, совпадение версии, отслеживаемое непустое
описание без `TODO` и отсутствие локального тега. Затем повторяет проверки на
итоговом коммите. Если после проверки изменили код или описание, повторите её.

## 3. Выпустить релиз

```powershell
git tag -a v0.4.0 -m "Vintage Story Panel 0.4.0"
git push origin HEAD
git push origin v0.4.0
```

Отправляйте коммит из ветки, в которой ведётся выпуск (обычно `master`). Отправка
тега запускает `.github/workflows/ci.yml`, который проверяет Linux и Windows,
собирает `linux-x64`, `linux-arm64`, `win-x64`, проверяет содержимое архивов и
публикует релиз с описанием из `docs/releases/0.4.0.md`.

Вложения: три платформенных архива, `get.sh`, `get.ps1`, `SHA256SUMS`. Стабильный
выпуск становится `latest`; версия с дефисом публикуется как prerelease.
Проверьте успешное завершение всех заданий в GitHub Actions и наличие всех шести
вложений в GitHub Releases. До этого выпуск не считается завершённым.

Если CI упал до создания релиза, исправьте причину. Для изменённого коммита используйте
новый номер версии; опубликованные теги и вложения не переписывайте. При временном
сбое без изменения коммита можно повторить неуспешные задания в Actions. Если остался
черновик релиза, сначала проверьте его состояние: повторное создание того же релиза
не поддерживается текущим workflow.

## Локальный пакет для проверки

Если нужен Windows-пакет до выпуска:

```powershell
pwsh -File scripts/publish.ps1 win-x64
```

На целевой Linux-машине:

```bash
bash scripts/publish.sh linux-x64
# или bash scripts/publish.sh linux-arm64
```

Результат лежит в `artifacts/<RID>`. Подготовка релиза сама пакеты не собирает и
программы не запускает. Установку, обновление, службы и работу игры проверяйте на
целевых машинах; локальные тесты этого не заменяют.
